## 写作标准

采用 Matt 的 `writing-for-agents`，按文档用途组织内容，无需所有文件套同一个模板。

- **入口说明何时读、读什么。** README 介绍项目并导航；AGENTS 指向执行规则。分支特有的长说明放入负责文件，通过明确的阅读条件抵达。
- **一个含义维护一处。** 业务规则归 CONTEXT，术语定义归 GLOSSARY；操作文档链接规则并说明怎样操作。同一概念的规则与例外放在一起，其他文件只引用。
- **步骤写到可判断完成。** 写明输入、动作和完成依据；参考资料按主题组织。明确区分已实现、已验证范围、计划与保留试验。
- **动态事实从源头查。** 版本、参数、提交与 CI 状态以代码、帮助、锁文件及 GitHub 为准。文档保存必要的操作方式、约定和取舍；历史证据保留当时版本与结果。
- **修改时删去失效说明。** 当前文件保持简短、正向、具体；不要在入口积累逐轮计数、对话调度或重复规则。第三方文档、生成报告和程序加载的提示词按其原用途维护。

## 档案生命周期

开始工作时查已有 [GitHub Issue](agents/issue-tracker.md)，其中保存问题、范围、验收及关联关系；当前进度和合并状态也查 Issue／PR。可复用的当前知识写入上表负责文件，不在任务日志复制整份说明。

维护产生值得保留的反例或验证时，放入 `docs/maintenance/YYYY-MM-DD-主题/`，由简短 README 关联 Issue／PR，说明比较版本、材料来源、复现方式、结果和局限；原始结果单独保存。工具对照继续放 `experiments/`。完成后从对应索引登记，重验证另存结果，保留旧事实。

现行说明被替代时，先确认新入口；需要追溯的旧正文移入 `docs/history/` 并登记适用时期。搬移只调整链接位置，保留当时参数、结论和缺口。常用旧路径保留简短跳转；无法恢复的历史链接明确说明原因，不能悄悄指向另一份材料。

`AGENT_HANDOVER.md`、`WORKBENCH.md` 和根目录 `REPORT.md` 是兼容入口。运行原件、输入表、复核数据库及凭据按 [备份规则](operations.md) 留在受控存储，公开 Git 仓库不能替代数据备份。Mission B 的独立工具文档由其目录维护，整理前核对该目录并发工作。

## 完成检查

检查所有改动的当前文档链接及阅读入口；核对搬移前后的原文，仅允许已说明的路径调整。当前说明应与实现相符，未验证能力保留限制。审查变更范围，确保业务契约、原件、人工决定和其他人的工作没有随整理改变；审查与提交后的核验按 [工作流](agents/workflow.md#完成条件) 完成。

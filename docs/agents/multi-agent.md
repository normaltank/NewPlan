# 多代理实施

仅在 [任务分流](workflow.md#任务分流) 选择 `implement-spec` 后读本页，同时读取已安装的 `to-spec`、`to-tickets`、`implement-spec`。这里约定本项目如何派工、保存证据和处理隔离；技能正文规定各阶段步骤。

## 规格与工单

规格说明用户问题、交付行为、实现与测试决定、范围边界。拆票沿完整业务路径划分，每票可独立演示或验证，并列出真正阻塞它的工单；大范围机械重构按 `to-tickets` 的兼容迁移例外拆分。由主代理先整理具体草案，按技能核对用户确认，再发布到 [GitHub Issues](issue-tracker.md)。

开始派工的条件是：规格与工单均可访问，验收和依赖明确，没有依赖环，测试边界及拆分已确认。重用已有确认的出处，不为同一决定重复询问。依赖的保存方式与状态更新规则统一见 [任务关系](issue-tracker.md#任务关系与-wayfinder)。

## 派工与隔离

主代理建立 `codex/` 前缀的集成分支，固定起点。按依赖选择当前可开始的工单；不依赖的工单可并行，受实际代理容量与改动冲突限制。共享文件的修改无法安全并行时串行执行并记录原因。

每个工单实际交给一个实施子代理，使用独立分支和工作树，按 [统一配置](workflow.md#子代理与上下文) 创建。任务消息至少包含：

- 角色、工单与规格、范围和验收指针；此前已确认的测试边界。
- 集成分支及起始提交、该代理专用工作树的绝对路径；所有命令和写入使用该路径。
- 已读取／需读取的技能与项目入口、允许修改的范围、需要返回的证据和阻塞报告方式。

代理启动时核对实际 Git 根目录、分支和集成起点。发现错误基线时，保留已有修改并由主代理安排安全重建或合入正确基线；不对有修改的工作树直接重置。共享工具的默认工作目录可能变化，不能据此推断自己的写入位置。

实施子代理读取 `tdd`，逐项完成红→绿及工单验证。报告完成前合入当时的集成分支顶端并验证受影响行为；返回提交、测试与反例结果、剩余限制。发现超出工单的修改时先回报，不能静默扩大任务。任务记录写明实际完成者，主代理亲自完成的工作如实记录。

## 集成与整体交付

1. **合入一票。** 主代理派出合并子代理，在专用集成工作树中一次处理一份成果，核对工单、提交和验证证据后合入。存在冲突时保留双方意图并验证；需求冲突回到主代理处理。主代理协调期间不并发写入该工作树。
2. **释放依赖。** 记录合入提交及集成验证。只有所需前置成果已合入且相应验收通过，后续工单才可启动；收到“已完成”消息本身不代表依赖已满足。首个成果合入后，按已授权范围创建关联规格和工单的草稿 PR。
3. **整体审查。** 全部工单集成后，对固定集成版本执行验证与 `code-review` 的双维度审查。把审查修复集中交给一个实施子代理，修复后补足受影响的验证和复审，再标记 PR 可审查。
4. **交付。** 按 tracker 的关闭方式处理工单，不因分支已有提交或草稿 PR 已建立就关闭。保留各票独立结果和整体证据；CI、工作树清理及最终答复遵守 [完成条件](workflow.md#完成条件)。

## 执行证据

在 [任务执行记录](issue-tracker.md#执行记录) 中关联每票的实施代理、工作树／分支、起始与产出提交、验证、合并代理和集成提交，再链接整体审查及 CI。记录标明失败、撤销或主代理接手的情况。

完整多代理实施需要实际的实施与集成记录；只有计划、配置、工单或两名审查代理时，报告对应阶段已完成和实施尚未执行。流程配置可以用文档审查验证，未来真实多工单任务完成前不宣称该实施流程已端到端验证。

# Matt 技能工作流

开始开发、维护或档案任务时读本页，先选路线，再进入对应技能。业务要求见 [CONTEXT](../../CONTEXT.md)，文档写作和存放位置见 [文档管理](../README.md)。本页规定项目执行与验收约定，技能正文仍是各阶段的流程来源。

## 任务分流

1. **读取实际技能。** 从会话清单或已安装的用户技能目录（通常为 `~/.codex/skills/`）读取 `ask-matt/SKILL.md`，再读取所选技能。父级 MyPlan 的同名副本不是默认来源。必要技能缺失时报告并按安装流程处理；记录采用来源，不将本地安装版本宣称为上游最新版。
2. **承接需求。** 查已有 Issue、用户决定、交付项与测试边界。新想法按 `grill-with-docs` 澄清；难复现故障先按 `diagnosing-bugs` 建立可验证的反例，再判断实现规模。既有需求与确认直接沿用。
3. **记录选路。** 按下表决定，在 [任务执行记录](issue-tracker.md#执行记录) 写明理由，并向用户简短说明。文件数量或代理数量不能单独决定任务规模。

| 判断依据 | 执行路线 | 进入实施前的条件 |
| --- | --- | --- |
| 一个可独立验收的结果，能在当前上下文完成 | 代码用 `implement`；纯文档用 `writing-for-agents` | Issue 已明确范围、验收、验证方式及不拆分的理由 |
| 多个需要分别验收的交付项，或需要跨上下文实施 | `to-spec` → `to-tickets` → `implement-spec` | 规格、工单、依赖和用户确认可追溯；随后读 [多代理实施](multi-agent.md) |
| 用户明确选择逐票推进已有规格 | 按依赖逐票 `implement` | 每票使用独立上下文；仍保留规格、依赖与整体验收 |

较大任务默认采用 `implement-spec` 调度实施子代理，主代理负责协调和验收。无法派工时报告具体限制与未执行步骤，不用审查代理替代实施代理。探索中发现规模变化时，先更新原 Issue 的路线和依赖，再继续；不要把需要拆分的任务永久留在主代理手中。

`to-spec`、`to-tickets`、`tdd` 要求的确认，先核对会话中已有的需求、拆分和测试边界。缺少确认时给出完整可审阅草案，只问未决部分，并说明具体技能来源；现有授权持续有效。任务授权统一按 [AGENTS](../../AGENTS.md#授权与维护)，技能不扩大范围。

## 验证与审查

代码实施读取 `tdd`，在已确认的外部行为边界逐项红→绿；难故障保留原反例回放和既有成功样本。纯文档检查内容、链接、锚点和变更范围，不新增用于证明文档文字存在的业务测试。

完成改动后读取 `code-review`，固定比较基线、受审提交、需求来源与规范来源，实际派出 Standards、Spec 两名独立审查子代理。分别保存两份结论；新增改动对审查结论的影响要明确，必要时复审。多代理实施路线的审查修复按 [集成约定](multi-agent.md#集成与整体交付) 执行。

写 PR 时读取 `pr`，按仓库 [PR 模板](../../.github/PULL_REQUEST_TEMPLATE.md) 提供问题与结果、前后证据、影响范围，并链接任务执行记录。报告实际执行：读过技能、配置了流程、子代理审查过代码，都不能当作已经完成子代理实施的证据。

## 子代理与上下文

子代理统一显式设置 `model="gpt-6.1-sol"`、`reasoning_effort="high"`、`fork_turns="none"`，并提供完成任务所需的指针与边界；后续委派遵守同一配置。复用前核对配置，无法确认则新建；指定模型不可用时报告，由用户决定替代模型。

技能要求的临时子代理属于当前任务。创建或发送任务到独立用户对话需要用户明确安排，不能用既有对话代替实施或审查子代理。派工记录应标明角色，不能只记录一个代理总数。

阶段切换按 `ask-matt/PHASE-BOUNDARIES.md` 决定继续、压缩、交接或派工。需求到拆票阶段保留必要原始上下文；阶段变化通过 Issue 和证据指针承接，不建立另一份长期任务流水账。

## 完成条件

逐项满足所选路线的验收条件后收尾：

- Issue 能追溯选路、已确认的范围、实际角色与工作成果，未执行步骤明确说明。多代理路线另满足 [派工与集成证据](multi-agent.md)。
- 验证记录对应实际交付版本；Standards 与 Spec 分别报告。当前说明已写回 [负责文件](../README.md)，旧事实和运行原件保留。
- 已提交版本的 CI 跟踪到最终结果；获授权合并时再跟踪合并提交。交付到 PR 待审阶段与已合并分别报告，不擅自扩大为合并或部署。
- 工作树清理前确认成果已保存、未提交或忽略文件是否仍需保留；保留其他人的工作。最终答复说明结果、版本／PR、验证范围及剩余限制。

等待 CI 或子代理时使用可中断的短等待，单次不超过 60 秒；运行期间持续说明阶段与实质进展。连续 10 分钟没有可核实进展时检查执行服务与任务状态，报告已完成项、待完成项和阻碍，不把停止等待当作验收通过。中断后先核对准确提交或代理状态，避免重做；确认完成后立即写记录并给最终答复，不继续扩展任务。收尾出现遗漏或明显延误时按 `retro` 记录原因和环境改进。

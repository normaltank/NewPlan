# Matt 技能工作流

开始新的开发、维护或档案任务时读本页；业务要求见 [CONTEXT](../../CONTEXT.md)，文档写作和存放位置见 [文档管理](../README.md)。这里规定本项目如何接入技能，具体步骤以实际读取的 Matt `SKILL.md` 为准。

## 选择与执行

1. **确定技能来源。** 从会话技能清单定位 Matt 技能；清单未列出时，检查已安装的用户技能目录（通常为 `~/.codex/skills/`）。读取 `ask-matt/SKILL.md` 路由当前任务，再读取所选技能的正文。以 [Matt 官方仓库](https://github.com/mattpocock/skills) 核对来源；父级 MyPlan 的同名副本属于旧项目资料，不是本项目默认实现。必要技能缺失时明确报告，按安装流程补齐，不能只凭技能名声称已执行。
2. **确定任务与验收。** 按 [任务管理](issue-tracker.md) 找到已有 Issue，缺少时记录当前获授权的工作范围、验收条件和证据位置。只有需要跨会话拆分的工作才增加规格与子任务；明确的小任务在当前会话继续。路线由 `ask-matt` 决定，本页不复制各技能的流程树。
3. **执行所选路线。** 改 Markdown 前读 `writing-for-agents`；明确或修改领域术语时读 `domain-modeling`。涉及运行行为时，用具体反例和既有成功样本验证。纯文档整理用链接、内容保真和变更范围检查，不为此新增业务测试。
4. **审查与交付。** 改动完成后读 `code-review`，固定比较基线和需求来源，分别做规范与需求审查；修复发现的问题后记录结论。写 PR 时读 `pr`，附变更、前后证据和影响范围，并关联 Issue。

技能选择、读取位置和本轮验收条件先简短告知用户；实际证据留在 Issue／PR 或维护记录中。配置文件和技能安装成功只证明入口可用，不证明工作流已执行。

## 会话与子代理

当前会话默认承担当前任务。需要阶段切换时，先按 `ask-matt` 的 `PHASE-BOUNDARIES.md` 判断是否继续、压缩上下文、交接或使用子代理。

技能明确要求的临时子代理属于该任务，例如 `code-review` 的两个审查者；给它们限定比较范围和输出，再由主代理汇总结论。独立用户对话是另一个调度对象，创建或发送任务须有用户明确安排，不能用已有对话的名字替代技能调用。授权边界统一遵守 [AGENTS](../../AGENTS.md#授权与维护)。

本项目所有子代理统一使用 `gpt-6.1-sol`、思考强度 `high`。创建时显式设置 `model="gpt-6.1-sol"` 和 `reasoning_effort="high"`，并将这条要求传递给后续委派；它不新增委派授权。复用已有子代理前确认其配置，无法确认时以指定参数新建；模型不可用时报告限制，由用户决定替代模型。

当前协作工具需要将 `fork_turns` 设为 `none` 或指定轮数才能覆盖模型与思考强度；采用这些方式时，向子代理提供完成任务所需的上下文。

## 完成条件

本轮验收条件逐项有证据；未验证项明确写出。规范和需求审查分别报告，未执行或受阻的步骤如实注明。已提交变更的 CI 跟踪到该提交的最终结果，代码正确性与学院完整性仍按 CONTEXT 分开判断。

当前说明已更新到负责文件，复现和结果已能从 Issue／PR 找到；遗留问题单独记录。交付时给出版本、验证范围和剩余限制，达到约定验收点后停止。

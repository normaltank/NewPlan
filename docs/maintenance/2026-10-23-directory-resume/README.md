# 初采与续采的名单解析一致性

基线：`00ea5f9a5c22838faa0199ec0fb8451d76c46508`。目录解析机制：`directory-interpretation-v1`；原有嵌套卡片恢复机制仍为 `nested-directory-card-v1`。

## 问题与根因

初采 `Pilot.roster` 和续采 `restore` 各自解释一次名单行。初采已经支持空排版链接后的姓名、显式分组标题，以及不规范嵌套卡片；续采直接执行原始选择器，再取第一个标签，没有应用这些规则。相同保存页由此产生不同人员证据。

隔离复现中，空链接后的“张三”在初采有一条观察记录，续采变成零条；“李四”的行政教辅分组在续采后消失，后续不能再核验该分组。已有嵌套名单样本初采恢复九条，而模拟旧版只保存三条时，旧续采仍只能得到三条。这里的数量是样本页观察记录数，不能推算全院交付人数。

## 修改

[directory_rows.py](../../../directory_rows.py) 的 `parse_directory` 统一处理行恢复、姓名、链接、分组和非人员条目，按原始条目顺序返回结果。初采与续采共用这一解释；采集范围判断和任务入队仍由原有 `Pilot.register` 执行。姓名与选择器辅助函数迁入该模块，`api_pilot` 保留导入名称；迁移前后函数语法树一致。

续采替换观察记录前，同时核对行数和原有姓名／规范化链接能否重建。无法重建时保留原观察记录，并在新运行的 `resume.json` 中记录 `skipped_rosters` 及原因；成功重建时同步条目数和嵌套恢复依据。只写新运行目录，旧材料保持原样。

## 验证

- [新增回归](../../../test_directory_resume.py) 通过真实 `Pilot.roster → 保存文件 → restore` 调用链验证。最初六项用例在基线上有四项失败；修复后连同采集顺序保护，共七项通过。
- 保留并验证已有成功行为：普通名单、生僻字与英文姓名、只有名单无主页、非人员资料链接、跨子站范围限制，以及非合格来源不能追加个人页工作。
- 新增用例逐文件比较旧运行材料的 SHA-256；新旧目录均在临时目录，模型替身一旦收到调用就报错。没有使用正式数据库或付费模型。
- 根目录全部 **203 项测试通过**，包含已有人工决定继承、材料变化后不沿用旧确认、三表交付和访问控制检查。
- 重构中发现分开收集人物与资料链接会改变任务顺序，已改为按条目顺序消费，并加入专门回归；采集上限下的先后顺序保持原有行为。

命令、结果与源文件哈希见 [validation.json](validation.json)，执行记录见 [修复前](before.txt)、[完整回归](after.txt)。GitHub 对应提交的 CI 以仓库检查页面为准。

## 范围与限制

本次验证为本地合成反例、已有保存页及隔离回归，没有重新采集大学网站，不证明全院完整性。续采仍只处理未访问页面，旧失败页不会自动重试。正式运行材料与人工决定没有批量重写；运行中的旧进程也没有重启。

此前架构调查发现的另一项“正文变化未进入评估缓存指纹”问题未包含在本次修复中，需要独立处理。

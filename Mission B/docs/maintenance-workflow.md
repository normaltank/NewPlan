# Mission B 维护执行约定

开始维护、接收一批新日志或发现新的独立根因时读本页。技能来源、授权、子代理模型、任务管理及通用收尾条件以 [公共 Matt 工作流](../../docs/agents/workflow.md) 为准；业务边界以 [URL 核验口径](../SmallMission/api_workbench/README.md#核验口径) 为准。本页补充 Mission B 的任务切分和证据要求。

## 确定路线

先在对应 Issue 记录本轮问题、验收目标、样本范围、比较基线和路线理由。用可独立验收的修复目标判断工作量：

| 情况 | 执行方式 |
| --- | --- |
| 只有一个可独立验收的目标，缺陷维护仅涉及同一根因，且能在一个实施上下文完成；如兼容一种输入格式、调整一组界面与导出列名 | 小任务路线；缺陷先用 `diagnosing-bugs` 建立失败回放，按所选实施技能完成验证和审查 |
| 多个独立根因、多个可分别验收的修复目标，或需要跨实施上下文完成 | `to-spec → to-tickets → implement-spec`；规格、依赖工单和实施子代理均须实际执行 |
| 单一纯文档调整 | 在当前会话修改，用链接、规则情景和变更范围验证；不为文档增加业务测试 |

同一根因影响多个学院，可共用一个切片和一组对照材料。一次日志维护同时涉及输入识别、名单区域和分页等独立问题时，分别建立含自身验证的切片。按机制与验收结果分流，不按学院数或文件数机械拆票。

小任务中出现新的独立目标，先保留反例和已完成结果；在继续该目标的实施前，重新判断路线并更新规格与依赖工单。既有验收和确认可沿用；技能要求而尚未取得的确认，按公共工作流提交具体方案后处理。

## 拆分与派工

父任务保存目标、范围、公共约束和整体验收；每张子工单写明一个可验证结果、自身的失败／成功对照、阻塞关系和完成条件。字段与 GitHub 关系操作见 [任务管理](../../docs/agents/issue-tracker.md)，记录集中在 Issue，不另建长期任务流水账。

采用 `implement-spec` 时，按其任务图分派无未解决阻塞项的工单：实施子代理在各自分支和工作树修改，经合并子代理进入集成分支。实施回报必须含实际提交、验证结果和剩余限制；只返回分析或审查意见不算实施完成。依赖任务在前置结果已集成且对应验证通过后才能开始。

派工上下文以规格、工单、证据和提交的指针为主，补充本次写入范围、当前集成基线以及已授权的运行范围。工作树存在他人修改时先保留，使用干净工作树同步基线；不为执行技能中的重置步骤覆盖未提交工作。

在任务记录中分别关联实施、合并、规范审查和需求审查的实际代理、分支／工作树、提交与验证证据。单任务直接实施也如实记明执行者。两个审查子代理的报告不能代替拆票、实施和集成记录。其他用户对话的资料不代替这些角色。

## 核验与分发证据

每个切片在自身范围内闭环，集成后再核对组合行为：

- **输入维护**：验证用户原件的解析结果、既有成功格式及歧义输入；原件保留。
- **名单或分页维护**：用实际失败材料建立可判失败的回放，并检查已有成功样本。记录入口、已读取页面、未决范围及逐 URL 差异；测试通过不替代名单完整性证据。
- **输出维护**：检查实际页面、下载汇总和错误学院更新文件的一致性；三类结果及空说明按现有产品契约验证。
- **纯文档维护**：检查入口、相对链接与锚点，并用小修、多根因维护、执行中扩展范围等情景核对执行路径。

实跑在隔离数据库和输出目录进行。每个阶段保存输入来源、代码／提示版本、运行标识和结果位置，新结果写入新目录；原件、历史输出和失败记录保留。采集、付费调用和邮件仍按既有授权执行，不由工作流标签自动授权。

修改名单判断、分页逻辑或提示后，按影响复跑失败样本和成功对照。冻结计划回放只能证明对原计划的处理，不能声称验证了新提示的模型选择。需要分发时核对包内实现与最终验收版本；中间构建和最终交付明确区分。

## 收尾与复盘

按公共工作流完成独立双轴审查、相关验证、提交 CI 和工作树清理。归档位置见 [档案索引](README.md)；Issue／PR 引用具体记录，分别报告实际执行的阶段、未执行项及原因。没有实施代理记录时，仅报告单任务实施及独立审查。

构建或维护结束后执行 `retro`，依据本轮记录检查路线是否及时升级、子任务是否真正独立完成、材料是否被重复读取、阶段证据是否覆盖最终版本。可复用修正写入已有负责文件；无须新增规则时记录理由。公共流程问题反馈到公共工作流的维护任务，本页只维护 Mission B 的具体约定。
